# 비즈톡 경력기술

- 기업용 비즈메시지(카카오 알림톡 등) 발송 중계 서비스
- 비즈메시지 발송 및 결과 처리 API 백엔드 개발 담당
- 근속기간: 2022.10.17 - 2024.03.01
- 기술: Java, Spring Boot, MyBatis, Kafka, Redis, Jenkins, MariaDB

## 요약
- **주요 성과**
  - 비즈메시지 전송 요청을 처리하는 API 서버 개발·유지보수 및 Jenkins Pipeline 기반 CI/CD 구축
  - Kafka 이벤트 핸들링으로 발송·결과 데이터의 실시간 처리 성능 유지
  - 임계 기반 발송 실패 감지·실시간 알림 시스템 구축 — 수동 감시 프로세스 약 1시간/일 → 0분
  - 비즈메시지 이용 통계 조회 웹사이트를 1인 풀스택으로 전체 설계·개발
  - 발송 결과 Push 애플리케이션 백엔드 전체 개발 (Kafka Consumer + WebFlux 비동기 처리)
  - DB 과부하 지점을 Worker Application 분리·스케줄러 기반 파일 생성으로 개선

비즈메시지 전송 요청을 처리하는 핵심 API 서버를 개발·유지보수했습니다.

- Kafka를 활용한 이벤트 핸들링·데이터 처리로 높은 실시간 처리 성능 유지

### 발송 실패 감지·실시간 알림 시스템

- **기간**: 2023.06 - 2023.08
- **사용기술**: Spring Boot, Redis, Kafka, Slack Webhook
- **성과**: 수동 모니터링에만 의존하던 발송 실패 인지를 임계 기반 자동 감지·전파 체계로 전환 — 감지·알림 자동화율 100%, 수동 감시 프로세스 약 1시간/일 → 0분

자사 서버·발송 업체 장애, 고객사 요청 전문의 포맷 오류 등 다양한 원인으로 발송 실패가 급증하는 상황이 있었고, 이는 고객 서비스 품질을 저하시킬 뿐 아니라 신속히 인지하지 못하면 서비스 장애로 확산될 위험이 있었습니다. 당시 운영팀이 수동으로 장애 여부를 모니터링하고 있어 대량 실패를 즉각 인지하기 어려웠고, 특정 에러 유형이 1분 내 기준치(500건 이상)를 초과하면 사내 알림 채널로 운영팀에 실시간 전파하는 시스템을 구축해 해결했습니다.

- Redis INCR + TTL 기반 카운팅으로 1분 단위 동일 실패 유형을 집계, 임계치(500건) 초과 시 Kafka 장애 알림 토픽에 발행
- Spring Kafka Listener 기반 비동기 Consume — 실패 유형·에러 코드·발생 건수 등 메타데이터를 포함해 SMS·알림톡·Slack(Webhook API)으로 운영팀에 전파, 원인 파악 시간 단축
- 실패 건수가 많았던 업체별 정책적 거부 사유를 분석해 발송 정책을 최적화하고, 실패 유형별 사전 필터링 로직을 추가해 발송 실패율 감소에 기여

### 고객사 모니터링 서비스 — 비즈메시지 이용 통계 조회 웹사이트

- **기간**: 2023.03 - 2023.06
- **사용기술**: Spring Boot, MyBatis, Spring Scheduler, Spring Security, Thymeleaf, Bootstrap, DataTables.js
- **성과**: 수작업 정산 데이터 전달을 자동화된 조회 시스템으로 전환 — 1인 풀스택 프로젝트로 요구사항 분석부터 설계·구현까지 전 과정 수행

고객사는 매월 비즈메시지 발송 건수를 기준으로 정산을 진행했지만 이를 위한 조회 시스템이 없어, 개발팀이 일자별 로그 테이블을 수동 조회하고 엑셀로 병합해 고객사에 전달하고 있었습니다. 시간 소모와 수작업에 따른 데이터 누락 위험이 있어, 고객사가 직접 월별/일별 발송 건수·실패 내역을 조회할 수 있는 자동화 통계 시스템으로 전환했습니다.

- 월별/일별 발송 건수·실패 내역 통계 집계·조회 시스템 구축 — DataTables.js 기반 대시보드로 발송 내역 시각화와 엑셀 다운로드 제공
- RESTful API로 회원 관리 기능을 구현하고 Spring Security 기반 인증 시스템 구축
- 고객사의 온프레미스 단일 서버 제약과 대량 통계 조회 시 DB 쿼리 과부하를 함께 고려해, Spring Scheduler로 정기적으로 프로시저를 호출해 최근 30일 발송 내역 통계를 JSON 파일로 저장하는 방식으로 데이터 반환을 최적화
- 분단위 페이지 리로드로 준실시간(분 단위 갱신) 조회 제공 — 고객사가 발송 통계를 직접 조회하게 되어 운영팀 부담이 줄고, 수작업 병합 단계 제거로 수기 오류를 원천 차단

**회고**

- 데이터 증가에 따른 쿼리 속도 저하에 대비해 캐싱·SQL 튜닝을 개선 방향으로 검토
- 온프레미스 단일 서버에서는 스케줄러 기반 정기 작업이 정상 동작했지만, 멀티 인스턴스·클라우드 환경에서는 중복 실행 방지를 위한 Spring Batch 기반 배치 처리 도입이 필요하다고 판단 — 대량 데이터 처리와 성능 최적화 여지

### 발송 결과 Push Application

- **기간**: 2023.09 - 2024.01
- **사용기술**: Spring Boot, WebFlux, Kafka Consumer, Redis
- **성과**: Polling 방식의 발송 결과 확인을 콜백 기반 Push로 전환한 애플리케이션의 백엔드 전체 개발 — 불필요한 Polling 트래픽 절감(API 호출 약 30% 감소), Push 처리 성공률 99% 유지

고객사가 발송 결과 확인을 위해 API를 주기적으로 호출(Polling)하던 방식이 실시간성이 떨어지고 불필요한 트래픽을 유발해, Push 방식의 콜백 기반 발송 결과 통지 시스템을 설계·구현했습니다.

- Kafka Consumer로 발송 결과를 수신하고, Redis에 저장된 고객사 콜백 URL을 조회해 WebClient로 비동기 HTTP 요청 전송
- 논블로킹 I/O 기반 처리로 콜백 전송 대기가 스레드를 점유하지 않아 대량 발송 시에도 처리량 유지
- 실패 시 Exponential Backoff 방식으로 재시도하고, 최종 실패는 DLQ로 전송해 기존 Polling 방식으로 결과를 가져갈 수 있도록 폴백 구성

카카오 비즈메시지 발신에 필요한 프로필과 템플릿을 생성하는 API 서버를 개발·유지보수했습니다.
